# The Door — Paper Prototype (Phase 0a)

## 簡介

本文件是 Phase 0a 的 Paper Prototype——一份以 MD 純文字模擬圖格式呈現的低成本原型，用於與非工程師（PM、發布經理、非技術管理者）進行使用者測試。

**測試目標：** 驗證 The Door 的圖形語言規範是否讓非技術人員能在 10 分鐘內：
1. 理解系統的功能全貌（L1 功能總覽）
2. 理解系統的結構組成（L1.5 結構概覽）
3. 回答「這次改了哪裡」（Diff 視圖）
4. 識別至少一個刻意埋入的疑義點（Planted Doubt）
5. 說出「發現疑義後的下一步」（疑義路徑）

**場景設計：** 本 prototype 使用一個虛構的「線上商店」系統作為測試場景，包含使用者管理、商品瀏覽、訂單處理、通知、排程等常見功能。場景中刻意埋入兩個疑義點（Planted Doubts），用於測試使用者的識別能力。

**格式說明：** 本文件使用 `docs/phase-0a/visual-language-spec.md` §9 定義的 MD 純文字模擬格式。所有符號慣例（`[U]`/`[S]`/`[E]` 前綴、`──→`/`- - →`/`═══→` 箭頭、`[+]` 展開指示器等）皆遵循該規範。

## 場景說明：線上商店系統

**系統名稱：** 線上商店（Online Store）

**系統概述：** 這是一個提供商品瀏覽、訂單管理、使用者帳號管理的線上購物平台。系統包含 8 個主要功能，涵蓋使用者操作、定時排程、事件驅動三種觸發類型。

**功能清單：**

| # | 功能名稱 | 觸發類型 | 說明 |
|---|---|---|---|
| 1 | 使用者註冊 | 使用者操作 `[U]` | 新使用者建立帳號 |
| 2 | 使用者登入 | 使用者操作 `[U]` | 使用者驗證身份並進入系統 |
| 3 | 瀏覽商品 | 使用者操作 `[U]` | 使用者查看商品目錄與詳情 |
| 4 | 建立訂單 | 使用者操作 `[U]` | 使用者選擇商品並下單購買 |
| 5 | 退貨處理 | 使用者操作 `[U]` | 使用者申請退貨並處理退款 |
| 6 | 每日庫存同步 | 定時自動 `[S]` | 系統每日自動同步商品庫存數量 |
| 7 | 訂單確認通知 | 事件觸發 `[E]` | 訂單建立完成後自動發送確認通知 |
| 8 | 批次匯出功能 | **新增** `[+]` | ⚠ **此功能為新增且超出本次 Sprint 範圍** |

> **⚠ Planted Doubt #1：** 「批次匯出功能」是一個未預期的新增功能，不在 Sprint 12 的承諾範圍內。測試對象應能在 Diff 視圖中識別出此功能被標記為「超出範圍」。

```
═══════════════════════════════════════════════════════════════
  📍 L1 功能總覽
═══════════════════════════════════════════════════════════════

┌─ 使用者管理 ─────────────────────────────────────────────┐
│                                                           │
│  [U] 使用者註冊                                           │
│  [U] 使用者登入                                           │
│                                                           │
└───────────────────────────────────────────────────────────┘

┌─ 商品與訂單 ─────────────────────────────────────────────┐
│                                                           │
│  [U] 瀏覽商品                                             │
│  [U] 建立訂單                                             │
│  [U] 退貨處理                                             │
│  [S] 每日庫存同步                                         │
│  [E] 訂單確認通知                                         │
│  [+] 批次匯出功能 .................. [⚠ 超出範圍 · 新增]  │
│                                                           │
└───────────────────────────────────────────────────────────┘

關係：
  使用者註冊 ──→ 使用者登入              "註冊後可登入"
  使用者登入 ──→ 瀏覽商品                "登入後可操作"
  使用者登入 ──→ 建立訂單                "登入後可操作"
  瀏覽商品 ──→ 建立訂單                  "選擇商品後下單"
  建立訂單 ──→ 訂單確認通知              "完成後觸發"
  建立訂單 ──→ 退貨處理                  "完成後可退貨"
  建立訂單 - - → 每日庫存同步            "可能相關"（推斷）
  批次匯出功能 ──→ 建立訂單              "匯出訂單資料"
```

**L1 圖形解讀：**

- **使用者管理**群組包含 2 個使用者觸發功能（`[U]` 圓角矩形）：使用者註冊和使用者登入
- **商品與訂單**群組包含 5 個使用者觸發功能、1 個定時觸發功能（`[S]` 平行四邊形）、1 個事件觸發功能（`[E]` 菱形），以及 1 個新增功能（`[+]`）
- 實線箭頭（`──→`）表示明確的因果關係，如「註冊後可登入」、「完成後觸發」
- 虛線箭頭（`- - →`）表示 LLM 推斷的可能關聯（「可能相關」），尚未經人工確認
- **⚠ 注意：** `[+] 批次匯出功能` 標記為「超出範圍 · 新增」，這是一個不在本次 Sprint 計畫中的意外新增功能

## L1.5 結構概覽

```
═══════════════════════════════════════════════════════════════
  📍 L1.5 結構概覽
═══════════════════════════════════════════════════════════════

  認證模組 — 處理使用者身份驗證與帳號管理 [+]
    由使用者請求觸發

  商品模組 — 管理商品資訊與庫存查詢 [+]
    由使用者請求觸發

  訂單模組 — 管理訂單生命週期與退貨流程 [+]
    由使用者請求觸發

  通知服務 — 發送訂單確認等各類通知給使用者 [+]
    由其他功能完成後通知

  排程服務 — 執行每日庫存同步等定時任務 [+]
    定時自動執行

  [基礎設施] 資料庫 | 快取 | 日誌 （點擊展開）

關係：
  認證模組 ──→ 訂單模組                  "呼叫"（驗證身份後操作訂單）
  認證模組 ──→ 商品模組                  "呼叫"（驗證身份後瀏覽商品）
  訂單模組 - - → 通知服務                "通知"（訂單完成後通知使用者）
  訂單模組 ═══→ [基礎設施]               "資料流向"（訂單資料寫入資料庫）
  商品模組 ═══→ [基礎設施]               "資料流向"（商品資料寫入資料庫）
  排程服務 ──→ 商品模組                  "呼叫"（定時同步庫存）
```

**L1.5 圖形解讀：**

- **5 個結構區塊**（圓角矩形）：認證模組、商品模組、訂單模組、通知服務、排程服務
  - 每個區塊帶有「模組名稱 — 功能說明」標籤
  - 每個區塊標示觸發機制（由使用者請求觸發 / 由其他功能完成後通知 / 定時自動執行）
  - 每個區塊帶有 `[+]` 展開指示器，表示可點擊展開至 L2 詳細視圖
- **基礎設施區塊**（圓柱 / subgraph）：資料庫、快取、日誌，收攏為一個可展開的區塊
- **實線箭頭**（`──→`）：直接呼叫關係（認證模組呼叫訂單模組和商品模組，排程服務呼叫商品模組）
- **虛線箭頭**（`- - →`）：事件通知（訂單模組通知通知服務）
- **粗線箭頭**（`═══→`）：資料流（訂單模組和商品模組的資料流向基礎設施）

- **`[−]` 移除**（紅色填充）：`舊版報表` 在 v1.3.0 中被移除，屬於範圍內的計畫性移除
- **`[~]` 屬性變更**（淺橘色填充）：`使用者登入` 的屬性發生變更（登入逾時調整），功能本身未改變
- **`[≠]` 依賴變更**（深橘色填充）：`訂單處理` 的依賴關係發生變更（金流 API 升級），比屬性變更更嚴重
- **未變更節點**（極淺灰，降調顯示）：`使用者註冊`、`瀏覽商品`、`退貨處理`、`每日庫存同步`、`訂單確認通知` 無變更，視覺上退到背景
- **邊的變更**：新增邊（綠色虛線）、移除邊（紅色虛線 + 刪除線）、修改邊（橘色實線）各一條
- **Diff + 範圍合併摘要**：一目了然地顯示範圍內變更 3 個、範圍外變更 1 個（需調查）、預期變更缺失 0 個

## 疑義路徑互動場景

以下展示使用者在圖形上發現疑義標示後的完整互動流程：從發現 ⚠ → 點擊查看詳情 → 選擇下一步。

### 場景：使用者在 L2 視圖中發現 ⚠ 標示

**前置情境：** 使用者已從 L1.5 展開訂單模組至 L2 詳細視圖，看到 `inventory_checker` 旁邊有一個 ⚠ 標示。

#### 步驟 1：使用者看到 ⚠ 標示

```
  ⚠ inventory_checker .............. [邏輯死路]
    └──→ order_service              "資料依賴"

  使用者注意到 ⚠ 符號和黃色填充 → 點擊 inventory_checker
```

#### 步驟 2：系統顯示疑義詳情面板

```
┌─────────────────────────────────────────────────────────┐
│  🔍 疑義詳情                                             │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  節點：inventory_checker                                │
│  所屬模組：訂單模組 > inventory_checker                  │
│  異常類型：⚠ 邏輯死路（Logic Dead-End）                  │
│  嚴重程度：3（中）                                       │
│                                                         │
│  異常描述：                                              │
│  分析發現 inventory_checker 中的條件判斷                  │
│  `if (stock_reserved && !stock_reserved)` 永遠為 false， │
│  導致庫存扣減邏輯永遠不會被執行。                         │
│                                                         │
│  發現時間：2024-01-20 14:32                              │
│  發現者：系統自動分析（LLM 推斷）                        │
│  目前狀態：已發現（尚未處理）                             │
│                                                         │
├─────────────────────────────────────────────────────────┤
│  下一步：                                                │
│                                                         │
│  [指派調查]     指派給工程師進行確認與修復                │
│  [直接升級]     升級至管理層決策（風險較高時使用）        │
│  [標記為已知風險] 確認此問題但暫時接受風險                │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

#### 步驟 3：使用者選擇下一步

使用者根據疑義的嚴重程度和自身角色，選擇其中一個行動：

| 選項 | 適用情境 | 後續狀態 |
|---|---|---|
| **指派調查** | 需要工程師確認是否為真正的問題 | 狀態變為「調查中」，指派給指定工程師 |
| **直接升級** | 問題明顯嚴重，需要管理層立即決策 | 狀態變為「已升級」，通知管理層 |
| **標記為已知風險** | 問題已知但目前可接受，不需立即處理 | 狀態變為「已解釋」，記錄接受風險的原因 |

**疑義路徑狀態流程：**

```
  已發現 ──→ [指派調查] ──→ 調查中 ──→ 已修復 / 已解釋
                                    └──→ 已升級（調查後發現更嚴重）
         ──→ [直接升級] ──→ 已升級 ──→ 管理層決定修復 / 接受風險
         ──→ [標記為已知風險] ──→ 已解釋（記錄原因）

  ※ 超時未處理 → 自動升級至管理層（超時規則在 Phase 3 定義）
```

## 測試任務清單

以下是 paper prototype 使用者測試的任務清單，供 3–5 位非工程師測試對象在 10 分鐘內完成。

### 測試任務

| # | 任務描述 | 預期正確回答 | 對應視圖 |
|---|---|---|---|
| 1 | 從 L1 功能總覽中，列出這個系統的主要功能（至少 5 個） | 使用者註冊、使用者登入、瀏覽商品、建立訂單、退貨處理、每日庫存同步、訂單確認通知、批次匯出功能（任列 5 個即可） | L1 功能總覽 |
| 2 | 從 Diff 視圖中，回答「這次改了哪裡」（列出所有變更） | 新增：批次匯出功能；移除：舊版報表；屬性變更：使用者登入；依賴變更：訂單處理 | Diff 視圖 |
| 3 | 在整個 prototype 中，找出至少一個被標記為「有問題」或「需要注意」的項目 | Planted Doubt #1：批次匯出功能（超出範圍 ⚠）或 Planted Doubt #2：inventory_checker（邏輯死路 ⚠） | L1 / L2 / Diff |
| 4 | 假設你發現了一個疑義標示（⚠），描述「接下來你會怎麼做」 | 點擊查看詳情 → 看到異常描述 → 選擇下一步（指派調查 / 直接升級 / 標記為已知風險） | 疑義路徑 |

### Go 標準

- **通過標準：** 5 位測試對象中 ≥ 4 位（80%）能在 10 分鐘內完成全部 4 項任務
- **單項任務通過定義：** 測試對象的回答涵蓋預期正確回答的核心要素（不要求逐字一致）
- **時間限制：** 10 分鐘（含閱讀 prototype 和回答問題的時間）

### 停損條件

- **觸發條件：** ≥ 3 輪迭代（每輪根據測試結果調整 prototype 後重新測試）後，仍有 > 50% 測試對象無法在 10 分鐘內完成全部任務
- **處理方式：** 停止迭代，進行圖形語言規範的根本性重設計（重新檢視視覺詞彙的可讀性、層級切換的直覺性、疑義路徑的可發現性）
