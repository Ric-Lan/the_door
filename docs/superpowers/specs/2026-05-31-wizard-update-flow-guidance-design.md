# Wizard 更新分析流程 — 引導式重設計（含相似度分流）

- 日期：2026-05-31
- 狀態：設計核可，待寫實作 plan
- 範圍：`docs/frontend-local-version-viewer/viewer/`（wizard 前端，唯一正式版）
- 性質：**純前端引導流程**，零新 HTTP endpoint

---

## 1. 核心原則（不可違背）

這個 wizard 是一個 **流程指示畫面（guidance screen）**，不是執行器。

- wizard **不執行**任何分析、不計算相似度、不跑 pipeline、不呼叫 LLM。
- wizard 能做的只有三件事：
  1. 依使用者的選擇，**決定要給哪一段指示**；
  2. **產生對應的指令文字**（CLI 指令 / MCP 指令），交給使用者貼給他的 LLM/agent 執行，或自己執行；
  3. 提供「結果該怎麼判讀」的**準則文字**。
- 結構抽取、相似度比對、差異解析，**全部由使用者的 agent 跑**（走專案既有的 agent-as-LLM 路徑：`extract_structure` → agent 自己比對節點重疊 → 回報相似度）。
- 因此本設計 **不新增任何 HTTP endpoint**。唯一用到的後端接口是「讀取既有快照清單」的唯讀接口（已存在）。

> 反模式警告：先前一版設計誤判為「需要補結構掃描 / 相似度 / 差異執行三個 endpoint」。
> 那是把 wizard 當執行器的錯誤框架。正確框架下，那些動作是 wizard **指示使用者去執行**的，
> 不是 wizard 自己呼叫的。

---

## 2. 現況問題

目前「更新分析」流程從操作選擇頁直接跳到「確認送出」頁，中間略過了所有設定步驟，導致：

1. 確認頁顯示的「版本標籤」是寫死的預設字串，不反映任何真實版本，容易誤導。
2. 流程完全沒有「要基於哪個既有版本」「要不要引入新資料」的分岔。
3. 沒有「這份新資料到底還算不算同一個專案」的判斷點，使用者拿到新版本資料時無從接續。

---

## 3. 目標流程（架構）

更新分析（已有快照時）後，進入一個 **更新方式分岔頁**，提供兩條路：

- **A 路 — 重生現有版本的解析**：不引入新原始碼，拿既有快照重跑 LLM 自然語言解析
  （例如 prompt 改了、或上次描述品質不佳要重來）。
- **B 路 — 引入新資料**：使用者下載/取得了一份新版本的原始碼資料夾，要判斷它跟既有版本的關係，
  並在「同專案新版本」的情況下做版本差異比較。

B 路的核心是一個 **相似度分流關卡**：必須先（由 agent）跑一遍結構比對得出相似度，
才能決定這份新資料是「同專案的新版本」（→ 做差異比較）還是「根本是不同專案」（→ 另存新專案）。

### 3.1 完整流程圖

```
操作選擇頁 ──更新分析──▶ 更新方式分岔頁
                          ├─ A 重生 ─▶ 重生指示頁（出指令，終點）
                          │
                          └─ B 引入新資料 ─▶ 新資料路徑頁
                                               ─▶ 結構比對指示頁（出指令）
                                                   ─▶ 相似度判讀/決策頁
                                                       ├─ 當作版本 ─▶ 快照標籤頁 ─▶ 確認送出頁 ─▶ 指令交付頁
                                                       └─ 當作新專案 ─▶ 導回首頁的「選新專案資料夾」流程
```

「快照標籤頁 → 確認送出頁 → 指令交付頁」沿用既有頁面，不重做。

---

## 4. 各階段行為（流程語言描述）

### 4.1 更新方式分岔頁

- 純選擇頁，兩個選項卡：A 重生 / B 引入新資料。
- 不做任何計算，只負責把使用者導向 A 或 B 分支。

### 4.2 A 路 — 重生指示頁

目的：讓使用者選一個既有版本，wizard 產生「請 agent 對這個版本重跑解析」的指令卡。

行為：
1. wizard 透過既有的**唯讀快照清單接口**讀出全部既有版本，列成可選清單。
2. 使用者選一個版本。
3. wizard 依**標籤優先序**（見 §5）決定要沿用的識別字串。
4. wizard 把該識別字串填進重生指令卡，交付使用者/agent。
5. 此頁是 A 路終點——重生不產生新版本標籤，不匯流到快照標籤頁。

### 4.3 B 路 — 新資料路徑頁

目的：收集「新資料在哪」與「要跟哪個既有版本比」。

行為：
1. 使用者輸入新版本原始碼資料夾的路徑。
2. wizard 透過唯讀快照清單接口列出既有版本，讓使用者選一個當 **比較基準（baseline）**。
3. 兩者都備齊後進入結構比對指示頁。

> ⚠️ 前提條件：B 路的結構比對需要 baseline 那側也有可比對的節點清單（持久化結構或非空的 source_nodes）。
> 已知部分舊快照存在 source_nodes 全空的資料品質問題（drift），這種快照當 baseline 時 agent 無從比對。
> 此前提的處理路徑見 §10。

### 4.4 B 路 — 結構比對指示頁

目的：指示使用者的 agent 跑結構層比對，得出相似度。wizard 自己不算。

行為：
1. wizard 產生一張指令卡，內容是「請你的 agent 對新資料路徑跑 `extract_structure`，
   與基準版本快照比對節點重疊，回報相似度（沿用幾個功能 / 變動幾個）」。
2. 指令卡帶入使用者剛選的新資料路徑與基準版本識別字串。
3. 使用者/agent 在自己的環境執行，得到相似度數字。
4. 使用者按「下一步」進入判讀/決策頁。

### 4.5 B 路 — 相似度判讀/決策頁

目的：把判讀準則攤給使用者，由使用者依 agent 回報的數字按鈕決定走向。
（分流方式採「攤數字給使用者確認」，非系統自動分流。）

行為：
1. wizard 顯示**判讀準則**（見 §6 門檻）：相似度高於門檻 = 同專案新版本；低於門檻 = 不同專案。
2. 提供兩顆決策按鈕：「當作版本比較」與「當作新專案」。
3. 數字由使用者從 agent 的回報自行對照；wizard 不自動讀取、不自動分流。
4. 按「當作版本比較」→ 進快照標籤頁（既有流程）。
5. 按「當作新專案」→ 導回首頁的「選新專案資料夾」流程（既有流程，不另做頁）。

### 4.6 匯流回既有頁

- **當作版本比較**：進既有快照標籤頁 → 確認送出頁 → 指令交付頁。
  最終交付的是「對基準版本做差異解析」的指令（API key 模式可自動跑；agent 模式出 MCP/CLI 指令）。
- **當作新專案**：交給首頁既有的切換/首次分析流程處理。

## 5. 標籤的讀取來源（重生沿用標籤的依據）

每個快照在硬碟上是 `.the-door/snapshots/` 內的一個獨立 JSON 檔，內含三層識別：

| 識別 | 性質 | 何時有值 |
|---|---|---|
| version_id | UUID，永遠存在 | 建立快照時自動生成 |
| label | 人給的標籤（選填，可為空） | 建立時有指定才有 |
| git_tags | 對應 git tag 清單（選填） | 建快照時該 commit 有 tag 才有 |

- **讀取管道**：前端透過既有的唯讀快照清單接口取得全部快照（含上述三層識別）。純讀取，非新 endpoint。
  （注意：wizard 目前的 API client 尚無讀快照清單的方法，需新增一個 fetch 呼叫去打這個**既有** endpoint，
  詳見 §10。）
- **沿用/顯示優先序**：`git_tags[0] → label → version_id`。有 git tag 用 git tag，沒有用人給的 label，
  再沒有才退回 UUID。

  > ⚠️ 實作注意：viewer 既有的顯示 helper（`layers.js` 的 `_snapLabel`）只做到 `git_tags[0] → label → null`，
  > **不退回 version_id**（標籤為空時回傳 null）。本流程的指令需要一個後端能解析的識別字串，所以
  > **退回 version_id 是本流程要新增的行為，不能直接沿用 `_snapLabel`**——否則遇到沒 label 也沒 git_tag 的
  > 快照會拿到空字串，塞進指令會壞掉。後端的 baseline 解析本來就同時接受 tag / label / version_id，
  > 所以退回 version_id 一定解得開。

---

## 6. 相似度門檻（判讀準則，非程式計算）

- 門檻只是**給使用者看的判讀準則文字**，wizard 不據此自動分流。
- 預設準則：相似度（沿用功能比例）**高於約六成**視為同專案新版本；**低於約六成**視為不同專案。
  邊界情況由使用者自行裁量——這正是採「使用者按鈕確認」而非自動分流的理由。
- 門檻數值寫在判讀頁的說明文字中，未來可調整，不影響流程架構。

---

## 7. 模式差異（API key vs Agent）

- **Agent 模式（無 API key）**：全程是引導畫面。每個會「執行」的步驟（重生、結構比對、差異解析）
  都由 wizard 出指令卡，交給使用者的 agent 跑。這是本設計的中心情境。
- **API key 模式**：既有的「同路徑重掃」更新（首次分析 / 更新當前專案）維持「確認送出 → 自動跑 pipeline →
  輪詢進度」既有行為，本設計不更動該段。
- **B 路（引入新資料）的模式例外**：新資料位於伺服器當前指向專案**之外**的資料夾，既有自動執行接口
  （`/api/analyze` 只能分析當前專案根）**無法**指向它。因此 B 路的版本差異分支**無論有無 API key，
  都終結於指令卡**（交付 `update --from-snapshot <ref> <newpath>` 或其 agent-as-LLM 等價指令），
  不接既有自動執行。這是「只引導不執行」原則在跨資料夾情境下的必然結果。

---

## 8. 階段指示器（rail）

操作選擇頁側邊的階段指示器目前是「選擇操作 / 設定範圍 / 快照標籤 / 確認送出 / 分析中 / 進入 Viewer」。
B 路會多出「結構比對」「相似度判讀」兩個視覺階段，需要對應補上；A 路因為是短分支終點，
階段指示器維持精簡即可。實際階段標籤文案於實作 plan 細化。

---

## 9. 非目標（YAGNI）

- 不新增任何 HTTP endpoint。
- wizard 不自動讀取 agent 回報的相似度、不自動分流。
- 不做檔案內容 hash / 監看資料夾 / 自動偵測新版本下載。
- 不修既有「首次分析」「查看快照」「切換專案」三條既有流程的內部行為（只在 B 路終點導向其中之一）。
- 不在本 spec 修復 regenerate 後端是否為空殼的問題——A 路出的是「給 agent 的重生指示」，
  不依賴 regenerate CLI 子指令的實作完整度。

---

## 10. 待實作 plan 細化的項目

1. 各指示卡的**確切指令文字**（A 重生指令、B 結構比對指令、B 差異解析指令）。
2. 新狀態接入既有 reducer 的具體寫法與既有頁面的銜接點。
3. 階段指示器的標籤文案與階段對應。
4. 既有更新流程「直跳確認頁」舊路徑的移除與既有測試的調整。
5. 判讀頁門檻文案的確切措辭。
6. **wizard API client 新增「讀快照清單」的呼叫**（打既有 endpoint，非新 endpoint；現有 client 無此方法）。
7. **標籤識別字串的退回邏輯**：實作 `git_tags[0] → label → version_id`，**不可**直接套用 `_snapLabel`
   （它停在 label→null）。
8. **baseline 無持久化節點的處理路徑（純引導文字，非偵測）**：快照清單接口只回傳
   `{version_id, timestamp, trigger, label, git_tags}`，**不含 source_nodes**，因此 wizard 無從、也不應自行偵測
   baseline 是否缺結構（偵測會違反「只引導不執行」原則）。改以引導文字處理：在結構比對指示頁/判讀頁附一段
   「若 agent 回報無法比對（baseline 缺結構資料），請先跑 `extract --as-version <baseline> <baseline_source>`
   補檔（不需 API key）再回來」。讓這個失敗模式有明確出口，不靜默卡死。
